# Loop 8 — the repository as a second signal

> **The figures below are loop 8 as it was registered and first run.** The rule gained two
> things afterwards — a one-for-one hunk counts on its own, and what the line became is
> written as a record — and the final table for both held-out sets is in
> `../loop9/README.md`. Both are kept: this is what the registered gate measured, that is
> where the mechanism ended up.

Pre-registered in `../PREREGISTRATION.md` ("loop 8"), engine frozen at `027a61b`, scenarios
and phrasings generated by `claude-haiku-4-5` afterwards from `gen_scenarios_prompt.txt` and
`generation_prompt.txt` (the model writes the test data; it is never in the engine or in the
measurement). No model runs in any cell.

## Result on the held-out set

`eval_all.py`, 30 cells per arm (10 scenarios × 3 phrasing styles), one shared store per
style, `final_<arm>_<order>.json`:

| order | arm | retired_a | kept_b | served_ok |
|---|---|---|---|---|
| adjacent | talk | 17/30 | 30/30 | 9/30 |
| adjacent | code | 23/30 | — | 11/30 |
| adjacent | **both** | **27/30** | 30/30 | **19/30** |
| adjacent | noise | 0/30 | — | 0/30 |
| blocks | talk | 6/30 | 30/30 | 0/30 |
| blocks | code | 23/30 | — | 11/30 |
| blocks | **both** | **25/30** | 30/30 | **15/30** |
| blocks | noise | 0/30 | — | 0/30 |

The registered decision rule is met on all three conditions: `served_ok(both) >
served_ok(talk)` in both orders (19 > 9 and 15 > 0), `retired_a(noise) = 0`, and `kept_b`
unchanged at 30/30.

Two things beyond the decision rule are worth reading off the table.

**The commit does not care about the order.** `code` scores the same 23/30 and 11/30 whether
the revision follows the decision immediately or ten decisions later; `talk` falls from 17/30
to 6/30. Every lexical rule in the engine depends on the two statements being near each other,
because that is the only thing that relates them when they share no words. A commit relates
them by value.

**The precision control is clean twice.** Commits of the same shape that swap a value the
decisions never mention retire nothing, in either order.

## The opaque-commit control

`--commit-msg opaque` replaces the subject `use vitest` with `update dependencies`, so the
commit contributes its diff and nothing else: `both` is 15/30 adjacent and 11/30 in blocks
(against 9/30 and 0/30 for the conversation alone), and `code` keeps its 23/30 retirements
while `served_ok` falls to 0/30 — the old decision is known to be dead and nothing in the
store names what replaced it. The replication and the full table are in `../loop9/README.md`.

## Development numbers, for the drop

The same grid on the loop-7 set, which the engine was written while reading, is in
`all_<arm>_<order>.json`: adjacent `talk` 17/30 → `both` 24/30, blocks `talk` 3/30 → `both`
19/30. The held-out `both` numbers are lower (19 and 15), which is the usual distance between
a set that was read during development and one that was not.

## What the remaining misses are

Two of the ten scenarios cannot pass the oracle at all, and they are published rather than
dropped: `bull` → `bullmq` and `npm` → `pnpm` are substrings of their own replacements, so
"the old value is gone from the tree" is false by construction and "the old value is not in
the answer" is false whenever the new one is. Three cells each, six in total, counted as
failures in every arm.

The rest are a retrieval problem rather than a detection one: `retired_a` is 27/30 while
`served_ok` is 19/30, so in eight cells the replacement is on record, active, and the question
does not reach it — the generated topic phrase ("JavaScript test runner") and the message
("jest for tests") share no word the index can match, and two of the three words in that topic
are in the read path's stop list. That is the same lexical ceiling [Z5], now on the read side,
and no part of loop 8 addresses it.

## Reproduce

```sh
cargo build --release
B=target/release/muninn
for o in adjacent blocks; do for arm in talk code both noise; do
  python3 crates/muninn-bench/experiment/loop8/eval_all.py --muninn $B --arm $arm --order $o \
    --phrasings crates/muninn-bench/experiment/loop8/heldout_phrasings.json \
    --scenarios crates/muninn-bench/experiment/loop8/scenarios.json \
    --out /tmp/loop8_${arm}_${o}.json
done; done
```

Every cell is deterministic: commit dates and session ids are fixed by the harness. They were
not at first, and one cell in thirty flipped between runs because a commit hash is part of a
commit record's text and that text is indexed — worth knowing before trusting a one-cell
difference in any grid that commits.
