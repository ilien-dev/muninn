# Loop 12 — can a vector pair a replacement with what it replaces?

`[Z3]` closed the embedding route for supersession on **ten** sentence-level pairs (true pair
first 4 times, no separating threshold). `[Z5]` is the ceiling that route was meant to break:
23 of 30 held-out replacements share no content word with what they replace, so no lexical test
can pair them, and on the plain head-to-head **14 of Muninn's 15 failing cells were a stale
value served as current**.

The half `[Z3]` did not measure is the one that identifies a decision: not the sentence, which
is mostly prose about why, but the **named value**. `examples/name_cosine.rs` embeds only
`extract::name_tokens` from each side and reports, per scenario, the rank of the true pair among
every candidate old decision.

On loop 2's development phrasings — **six** pairs — it read 5 of 6 ranked first, which is why
this was worth a second look.

## The measurement

Forty-five development phrasings over fifteen replacements a coding project might actually make
(`scenarios.json`, written by hand and drawn from no held-out set; the wording generated by
`claude-haiku-4-5` from `generation_prompt.txt`, as every phrasing set in this repository is).
Forty-two have a name on both sides.

```
true pair ranked first: 3/42
min true -0.101  vs  max cross 0.340  →  overlapping: no single threshold separates them
```

**Three of forty-two.** Chance on a forty-two-way choice is one in forty-two; this is three.
The loop-2 reading was six pairs and did not survive a larger one.

## What it closes

The vector cannot say *which* decision a replacement replaces, on names any more than on
sentences. Both halves of the route are now measured and both are closed, so `[Z5]` stands as a
ceiling for anything that works from the text of the two messages alone — which is why the
mechanisms that do work read something else: the commit that changed the file (the fourth
trigger, 27/30) and the assistant's own reply when it names both values (21% of real replies).

`generation_raw.json`.
